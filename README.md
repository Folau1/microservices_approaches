# Домашняя работа по теме "Микросервисы: подходы"

## Задание 1. Обеспечить разработку

Для обеспечения процесса разработки, хранения исходного кода, непрерывной интеграции и непрерывного развёртывания я предлагаю использовать Gitlab + Yandex cloud.

Во первых, Gitlab можно развернуть бесплатно на собственных серверах в сервисе Яндекс Клауда.
Во вторых, Gitlab предоставляет все необходимые инструменты, для хранение исходного кода, систему контроля версий Git, непрерывную интеграцию (CI) и непрерывную поставку (CD).
Для каждого микросервиса будет создан отдельных репозиторий. С системой аутентификации и авторизации пользователей, разработчики будут работать независимо друг от друга над своими сервисами. Настраивать каждый процесс сборки под себя.
Для автоматизации сборки будет использовать Gitlab CI/CD. Все настройки будут храниться в файле .gitlab-ci.yml. Сборки можно запускать автоматически при изменении кода либо вручную, передавая необходимые параметры.

Инфраструктура будет выглядеть следующим образом:

Yandex Cloud будет использоваться для создания виртуальных машин, на которых разместим GitLab и GitLab Runner.
GitLab будет отвечать за хранение исходного кода, управление репозиториями и CI/CD процессами.
GitLab Runner разместим на отдельных виртуальных машинах в Яндекс Клауде. Это позволит выполнять несколько сборок и тестов одновременно, а при увеличении нагрузки добавлять новые Runner.
GitLab Container Registry будем использовать для хранения собранных Docker-образов микросервисов.
Yandex VPC позволит организовать сетевое взаимодействие между виртуальными машинами и настроить правила доступа.

Также Gitlab поддерживает создание шаблонов CI/CD, использование своих Docker образов, настройка этапов сборки и хранения различных секретов. При необходимости можно спокойно подключить Hashicorp Vault.

### Вывод: 
Считаю связку Yandex Cloud + Gitlab эталонным решением для большинства задач, поскольку сам Gitlab закрывает основные требования к процессу разработки, а Янедкс клауд предоставляет облачную инфраструктуру, которую можно мосштабировать по мере роста.
Ещё хочется добавить, что можно использовать бесплатную редакцию Gitlaba, оплачивая только облако Yandex Cloud.

## Задание 2. Логи

Для централизованного сбора и анализа логов в микросервисной архитектуре я предлагаю использовать связку Vector + Elasticsearch + Kibana.

Vector будем использовать для сбора логов со всех серверов, на которых работают микросервисы. 

Чтобы повысить отказоустойчивость, сделаем дисковую буферизацию. 
В случае, если Elasticsearch будет не доступен, то логи будут сохраняться в буфере. Также необходимо контролировать свободное место на дисках.
Elasticsearch будет выступать в роли центрального хранилища логов. Он позволит индексировать записи и быстро выполнять поиск.

Kibana будем использовать для просмотра и анализа логов через веб-интерфейс. Разработчикам можно предоставить отдельные учётные записи с необходимыми правами доступа, чтобы они самостоятельно находили ошибки в своих сервисах.
Также в Kibana есть возможность сохранять поисковые запросы вместе с фильтрами и делиться ссылками на них с коллегами. Это удобно при расследовании инцидентов.

### Вывод:
Считаю данную связку, подходящей для микросервисной архитектуры. Поскольку она, позволяет централизованно собирать логи со всех серверов, организовать их хранение и предоставить разработчикам удобный инструмент для поиска и анализа ошибок. При правильной настройке буферизации и повторной отправки можно существенно снизить риск потери логов.

## Задание 3. Мониторинг

Для мониторинга состояния серверов и микросервисов предлагаю использовать связку Prometheus + Telegraf + Grafana.

Telegraf будем использовать для сбора метрик со всех серверов, на которых работают наши микросервисы. Он позволяет отслеживать использование CPU, RAM, HDD и сетевых ресурсов.
Также с помощью плагина inputs.docker можно собирать метрики Docker-контейнеров. Благодаря этому мы сможем отслеживать, сколько ресурсов потребляет каждый микросервис, например нагрузку на процессор, использование оперативной памяти, сетевую активность и дисковые операции. 
Для контроля занятого дискового пространства отдельными сервисами дополнительно настроим мониторинг их томов.

Prometheus будет выступать центральной системой сбора и хранения метрик. Для взаимодействия с ним в Telegraf настроим плагин outputs.prometheus_client, который предоставляет собранные метрики через HTTP-эндпоинт. Prometheus будет периодически опрашивать этот эндпоинт и сохранять полученные данные.
Также сами микросервисы будут предоставлять собственные метрики через /metrics. Например, количество HTTP-запросов, время ответа, количество ошибок и другие показатели, характерные для конкретного приложения.

Grafana будем использовать для визуализации всех собранных метрик. Она позволяет строить графики, создавать дашборды и выполнять запросы к Prometheus с использованием PromQL.
Предлагаю разделить дашборды на две категории:

Для DevOps-инженеров: нагрузка CPU, RAM, использование дисков, сетевой трафик, состояние Docker-контейнеров, доступность микросервисов и количество ошибок.
Для бизнеса: количество заказов, успешных оплат, регистраций пользователей и другие бизнес-показатели, предоставляемые самими микросервисами.

В Grafana можно настроить отдельные папки с дашбордами и разграничить права доступа между командами.
Также предлагаю использовать Grafana Alerting, чтобы получать уведомления при высокой нагрузке на серверы, нехватке дискового пространства, большом количестве ошибок или недоступности сервисов.

Вывод: считаю данную связку подходящей для мониторинга микросервисной архитектуры. Telegraf позволит собирать метрики серверов и контейнеров, Prometheus обеспечит их централизованное хранение, а Grafana предоставит удобный интерфейс для анализа состояния инфраструктуры и бизнес-показателей.
Дополнительным преимуществом является то, что Telegraf поддерживает множество плагинов, поэтому при необходимости мы сможем расширять мониторинг без внедрения большого количества дополнительных инструментов.
